# PostgreSQL review against OpenAI's scaling case

Reviewed 2026-08-13 against OpenAI's official article, [“Scaling PostgreSQL to power 800 million ChatGPT users”](https://openai.com/index/scaling-postgresql/). This is an architectural review, not evidence that this repository needs OpenAI-scale infrastructure today. Statements labeled **Article** summarize the source; statements labeled **Repository inference** are recommendations based on the code inspected at this revision.

## Executive assessment

The repository already has strong correctness foundations: durable outbox and cursor repair, fenced leases, `FOR UPDATE SKIP LOCKED` work claiming, partial indexes for runnable/expired work, bounded batches and retries, serialized migrations with lock/statement timeouts, admission controls, retention, and content-safe telemetry. Its largest PostgreSQL production gap is not sharding. It is explicit control and visibility of the connection/query budget across gateway and worker replicas.

Recommended order:

1. Add one reviewed PostgreSQL runtime profile with explicit pool limits, connection lifetimes, acquisition timeout, `application_name`, `statement_timeout`, `lock_timeout`, and `idle_in_transaction_session_timeout` for each service role.
2. Export content-free pool/query/transaction metrics and alerts, then load-test the aggregate connection budget against the deployment's maximum gateway and worker replica counts.
3. Isolate realtime-critical gateway traffic from background worker/outbox traffic through separate database roles, pool budgets, timeout classes, and—when measured read volume justifies it—a read endpoint/replica.
4. Establish query-plan and online-migration gates before adding replicas, caches, or shards.

## Findings and opportunities

| Area | Official case | Current repository evidence | Repository inference / improvement |
|---|---|---|---|
| Workload isolation | **Article:** OpenAI separates high- and low-priority traffic onto dedicated instances so a noisy low-priority workload cannot degrade critical requests; it also isolates products/services. [Source](https://openai.com/index/scaling-postgresql/#workload-isolation) | Gateway realtime durability, admission, worker leasing, and outbox publishing share PostgreSQL. Gateway constructs more than one `pgxpool` (`cmd/live-gateway/main.go`), while the worker has its own pool (`cmd/live-worker/main.go`). | Treat gateway session/reconnect writes as high priority and worker leases/outbox/retention as background. First isolate with roles, connection quotas, timeout classes, and metrics; later route safe stale-tolerant reads to a replica or distinct endpoint. Do not let worker autoscaling consume the gateway's reserved database capacity. |
| Connection pooling | **Article:** Connection storms exhausted PostgreSQL; PgBouncer in transaction/statement mode reduced active connections and connection setup time, with careful idle timeouts and regional co-location. [Source](https://openai.com/index/scaling-postgresql/#connection-pooling) | Runtime services parse a URL and accept `pgxpool` defaults; no explicit `MaxConns`, `MinConns`, max connection lifetime/idle time, health-check period, or pool-stat telemetry was found. The listener also opens a dedicated connection outside the pool. | Add explicit per-role pool configuration and validate the total: `max replicas × pools per process × max connections`, plus LISTEN and migration/admin headroom. Consider PgBouncer only after transaction semantics and prepared-statement compatibility are tested. Co-locate application, pooler, and database endpoint. |
| Primary load / replicas | **Article:** OpenAI protects the single writer by offloading reads, runs HA with a hot standby, and maintains multiple regional replicas with failure headroom. [Source](https://openai.com/index/scaling-postgresql/#reducing-load-on-the-primary), [source](https://openai.com/index/scaling-postgresql/#single-point-of-failure-mitigation) | The repository documents backup/restore and database-outage response, but has one `DATABASE_URL` and no read/write routing or replica-lag contract. | Keep all lease, cursor, reconnect-owner, feature-authority, and read-after-write operations on the primary. Inventory truly stale-tolerant reads before adding `DATABASE_READ_URL`; define maximum replica lag and automatic fallback/load shedding. Prefer managed HA first—read scaling is not a substitute for writer failover. |
| Query/index discipline | **Article:** A small number of expensive queries and multi-way joins caused severe incidents; OpenAI reviews ORM SQL, decomposes complex joins, and uses transaction-idle timeouts. [Source](https://openai.com/index/scaling-postgresql/#query-optimization) | Queries are handwritten and generally bounded. Runnable leases, expired leases, cursor reads, outbox work, reconnect cleanup, and coordinator replay have targeted/partial indexes. Schema integration tests assert index use for four representative query shapes, but they disable sequential scans and do not measure execution/buffer budgets. | Extend the existing plan tests with a sanitized representative dataset and `EXPLAIN (ANALYZE, BUFFERS)` budgets for the hottest lease/outbox/cursor/journal/retention queries. Track query digest latency and rows examined/returned without SQL parameters. Add runtime statement and idle-in-transaction limits so one stuck request cannot impede vacuum or realtime traffic. |
| Write pressure / MVCC | **Article:** PostgreSQL's MVCC produces write/read amplification, dead tuples, index bloat, and autovacuum tuning challenges under high write traffic; OpenAI reduces redundant writes and smooths writes. [Source](https://openai.com/index/scaling-postgresql/#cracks-in-our-initial-design) | Handoff progress, heartbeats, delivery state, attempts, reconnect owners, and retention update durable rows. Fencing/idempotency prevent correctness duplication, but frequent heartbeats/progress can still create physical churn. More importantly, every framework-event writer takes the same transaction-scoped advisory lock to guarantee commit-ordered global sequence allocation, serializing event-appending transactions across all tenants and conversations. | Measure update rate, advisory-lock wait, HOT-update ratio, dead tuples, autovacuum delay, table/index bloat, and WAL per handoff. Coalesce non-terminal progress updates and avoid rewriting unchanged values where semantics permit. Before high write scale, redesign the ordering contract toward tenant/conversation-scoped serialization or another commit-order mechanism, with replay/outbox invariants proven under concurrency. Tune per-table autovacuum only from measurements. |
| Caching | **Article:** OpenAI protects PostgreSQL from cache-miss storms using per-key locking/leasing so only one request repopulates a missing key. [Source](https://openai.com/index/scaling-postgresql/#caching) | Feature state is refreshed and `LISTEN/NOTIFY` is only an optimization; durable polling/cursors repair missed notifications. There is no broad database cache, which preserves clear consistency. | Do not cache lease ownership, reconnect fencing, cursors, or runtime authority without a precise invalidation contract. If repeated immutable/config reads become material, add request coalescing (singleflight/lease) and bounded TTLs before a distributed cache; test cache-outage fallback so misses cannot stampede PostgreSQL. |
| Rate limiting and failure handling | **Article:** Load is limited at application, pooler, proxy, and query layers; short retries are avoided because retry storms amplify overload, and targeted query load shedding accelerates recovery. [Source](https://openai.com/index/scaling-postgresql/#rate-limit) | The system has session admission, bounded queues, worker concurrency, deadlines, leased retries, and an operational handoff kill switch. The article's failure pattern—timeouts followed by retries—is still relevant to database reconnect/poll loops. | Add a database overload policy: acquisition deadline, bounded exponential backoff with jitter, retry budget, and fail-fast/load-shed behavior by workload priority. Alert on acquisition wait, timeout/error class, pool saturation, outbox lag, lease lag, and retry amplification. Keep realtime voice independent when durable async work is degraded. |
| Schema changes and backfills | **Article:** OpenAI permits only lightweight changes, uses a strict five-second schema-change timeout, creates/drops indexes concurrently, and heavily rate-limits backfills. [Source](https://openai.com/index/scaling-postgresql/#schema-management) | Migrations are serialized and use a 5s lock timeout but a 2m statement timeout (`migrations/embed.go`). Migration 8 adds a `JSONB NOT NULL DEFAULT` column. Backup/restore and disposable down/up checks are documented. | Keep the existing serialization, but add a production migration classifier: metadata-only, concurrent-index, expand/backfill/contract, or prohibited rewrite. A universal 5s statement limit need not be copied blindly, but each change should have a reviewed lock and runtime budget. Backfills need small resumable batches, rate limits, replication-lag/load guards, and pause/rollback instructions. |
| Vertical scaling and sharding | **Article:** OpenAI first optimized application/database behavior, enlarged instances, and added replicas. It moved shardable write-heavy workloads to sharded systems but left PostgreSQL unsharded because retrofitting sharding was complex and the read-heavy system retained headroom. [Source](https://openai.com/index/scaling-postgresql/#scaling-postgresql-to-millions-of-qps) | Tenant and conversation IDs are present in primary keys and most durable access paths, which is favorable for future partitioning, but there is no evidence that current limits require it. | Scale vertically and optimize first. Define objective triggers for partitioning/sharding: sustained writer CPU/I/O, WAL/autovacuum debt, p99 under load, storage growth, and inability to meet headroom after query/write reduction. If triggered, handoff/event history is more naturally partitionable by tenant/hash or time than cross-session authority tables. |
| Observability and capacity | **Article:** The architecture is operated with capacity headroom, near-zero replica lag, low p99 latency, and failure isolation; scaling replicas introduces WAL and failover complexity. [Source](https://openai.com/index/scaling-postgresql/#scaling-read-replicas), [source](https://openai.com/index/scaling-postgresql/#results-and-the-road-ahead) | Existing metrics cover queue depth/age, worker timing, outbox lag, expired leases, duplicate delivery, reconnect restoration, and stale output. Direct database pool, query, lock, WAL, replication, vacuum, and bloat signals were not found. | Add dashboards/SLOs for pool acquired/idle/total/max, acquire wait, query/transaction latency and error class, lock waits/deadlocks, connections by application/role, primary CPU/I/O/storage/WAL, replica lag, autovacuum age, dead tuples/bloat, and migration duration. Use operation names—not raw SQL, arguments, transcripts, tool content, or credentials. |

## Concrete implementation backlog

### P0 — before production scale-out

- Define `store.pool` settings in strict config and include them in the config hash: role-specific maximum/minimum connections, acquire deadline, max lifetime with jitter, max idle time, health check, and safe session timeouts.
- Use a single reviewed pool factory so gateway, worker, admission, feature storage, listener, and migration connection accounting cannot silently diverge.
- Produce a deployment-time connection-budget check using HPA maxima, not current replica counts. Reserve writer connections for migrations, HA/operations, and critical gateway work.
- Export privacy-safe pool and database-operation metrics; alert before connection exhaustion and on outbox/lease lag rather than waiting for user-visible timeouts.

### P1 — validate under representative load

- Add database-specific load tests that combine maximum gateway sessions, worker concurrency, outbox publishing, reconnect churn, and retention; inject cache/notification loss and PostgreSQL latency to verify bounded recovery without retry storms.
- Add plan-regression fixtures for lease acquisition, outbox claim, cursor replay, coordinator journal, reconnect cleanup, and retention deletion.
- Benchmark and instrument the global event-append advisory lock; set an explicit throughput/lock-wait threshold that triggers a scoped ordering redesign.
- Separate gateway and worker database roles with least privilege, independent connection quotas, `application_name`, timeouts, and operational dashboards.
- Add online migration policy/tests, including concurrent-index and rate-limited resumable backfill patterns.

### P2 — only when measurements justify it

- Add read replicas for explicitly classified stale-tolerant queries with lag monitoring and failure behavior.
- Add request coalescing or caching only for measured repeated reads, with stampede protection.
- Partition or shard write-heavy history only after vertical capacity, query/index discipline, write coalescing, and archival/retention are insufficient.

## What not to copy mechanically

OpenAI's nearly 50 replicas, PgBouncer topology, five-second schema timeout, and migration of new tables to a sharded database are responses to its own scale and workload. The transferable lesson is to protect the primary through measured headroom, workload isolation, explicit connection/query bounds, safe migrations, and load shedding—not to reproduce the topology prematurely.
